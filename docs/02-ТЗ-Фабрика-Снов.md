# «Фабрика Снов» — Техническое задание (ТЗ)

**Связанный документ:** 01-GDD-Фабрика-Снов.md
**Целевая платформа:** Roblox (Luau), клиент-серверная модель
**Аудитория документа:** разработчик(и)/AI-агенты, ведущие реализацию в Roblox Studio

---

## 1. Технологический стек

- **Движок:** Roblox Studio, язык Luau.
- **Синхронизация кода с файловой системой:** Rojo (обязательно для работы через Claude Code — см. файл 03).
- **Хранение прогресса:** DataStoreService, обёрнутый в библиотеку профилей (рекомендуется ProfileStore / аналог ProfileService — session-locking, защита от потери данных при рестарте сервера).
- **Монетизация:** MarketplaceService (GetProductInfo, PromptGamePassPurchase, PromptProductPurchase, ProcessReceipt).
- **Сеть:** RemoteEvent/RemoteFunction через ReplicatedStorage, сервер — источник истины по всей экономике.
- **Тестирование:** ручной плейтест + модульные тесты бизнес-логики (чистые Lua-модули без прямой зависимости от Instance, чтобы их можно было юнит-тестировать вне Studio через `lune`/`roblox-cli`, если используется CI).

## 2. Архитектурные принципы

1. **Сервер авторитетен всегда.** Клиент не хранит и не считает валюту/редкость/шансы — только отображает данные, присланные сервером, и отправляет намерения (intent) через RemoteEvents.
2. **Модульность.** Каждая система — отдельный ModuleScript с чётким публичным API (Init, на входе — Player/данные, на выходе — события/результат). Никакой системы, которая напрямую лезет во внутренности другой — только через опубликованный интерфейс или Signal.
3. **Данные — декларативны.** Конфиги (цены апгрейдов, редкости петов, параметры биомов) выносятся в отдельные ModuleScript-таблицы (`Config/`), а не хардкодятся в логике — это позволяет балансировать без переписывания кода.
4. **Идемпотентность транзакций.** Любая операция, тратящая валюту или выдающая предмет, обёрнута в единую функцию с проверкой «хватает ли средств» и атомарной записью — не два отдельных шага, которые можно разорвать эксплойтом/рассинхроном.

## 4. Модель данных игрока (DataStore Schema)

```lua
type PlayerProfile = {
    Currency = {
        Essence: number,
    },
    Factory = {
        Level: number,
        StorageCapacity: number,
        ConveyorSpeedLevel: number,
        Decor: {string}, -- id купленных косметических предметов
    },
    Collection = {
        RadiusLevel: number,
        SpeedLevel: number,
        AutoCollectorOwned: boolean,
    },
    Pets = {
        {
            Id: string,        -- уникальный UUID экземпляра
            SpeciesId: string, -- ссылка на PetRarityConfig
            Rarity: string,
            Mutation: string?,
            Level: number,
            Equipped: boolean,
        }
    },
    Rebirth = {
        Count: number,
        ClarityMultiplier: number,
        CurrentBiome: string,
    },
    Chaos = {
        PersonalContributionToday: number,
    },
    PvP = {
        ShieldExpiresAt: number?,
        LastRaidedAt: number?,
        GuardsPlaced = {string},
    },
    Monetization = {
        GamePassesOwned = {string},
        BattlePassSeasonId: string?,
        BattlePassTier: number,
    },
    Meta = {
        FirstJoinAt: number,
        LastLoginAt: number,
        SchemaVersion: number, -- для миграций схемы данных
    },
}
```

**Важно:** `SchemaVersion` обязателен с первого дня — любое изменение структуры в будущем проходит через функцию миграции при загрузке профиля, иначе на живых игроках это приведёт к потере/порче данных.

## 5. Системы: спецификация по каждому модулю

### 5.1 CollectionSystem (сервер)
- Спавнит фрагменты в зонах локации по таймеру/пулу (server-side, клиент только видит результат через ReplicatedStorage-модели или через FastCast/визуальный стриминг).
- Принимает RemoteEvent `RequestCollect(fragmentId)` от клиента, **валидирует на сервере**: дистанцию игрока до фрагмента, существование фрагмента, кулдаун.
- При успехе — увеличивает буфер «сырых фрагментов» игрока (до `StorageCapacity`), удаляет фрагмент из мира, рассылает эффект всем через RemoteEvent для визуала.
- Авто-коллектор (геймпасс) — серверный таймер, который сам «собирает» ближайшие фрагменты без RemoteEvent от клиента.

### 5.2 FactorySystem (сервер)
- Конвертирует сырые фрагменты в Essence с задержкой на игрока (очередь конвейера), скорость зависит от `ConveyorSpeedLevel`.
- Функция покупки апгрейда: `PurchaseUpgrade(player, upgradeId)` → проверка цены по `UpgradeConfig`, списание, применение эффекта, сохранение в профиль.
- Публикует событие `OnEssenceProduced(player, amount, emotionType)` — используется ChaosBossSystem для обновления общей шкалы.

### 5.3 PetSystem (сервер)
- `HatchCocoon(player, cocoonId)` — сервер бросает кубик по таблице шансов из `PetRarityConfig` (шансы **не хранятся на клиенте**, чтобы их нельзя было подсмотреть/подделать).
- Мутации — отдельный ролл поверх редкости, с собственной низкой вероятностью.
- `EquipPet(player, petInstanceId)` / `UnequipPet` — лимит активных петов проверяется по владению геймпассом доп. слотов.
- Бонусы петов пересчитываются в единый агрегированный модификатор при каждом изменении состава активных петов (кэшируется, не пересчитывается на каждый тик).

### 5.4 RebirthSystem (сервер)
- `PerformRebirth(player)` — проверка минимального порога валюты/уровня, сброс `Currency`, `Factory` (кроме декора), `Collection` до базовых значений, инкремент `Rebirth.Count`, пересчёт `ClarityMultiplier` по формуле из `BiomeConfig`, разблокировка нового `CurrentBiome`, если достигнут порог.
- Все множители rebirth хранятся как чистое число, применяемое к финальному выходу Essence в FactorySystem — не разбрасывать логику по разным местам.

### 5.5 ChaosBossSystem (сервер, per-server state, не персистится в DataStore)
- Серверная (не игрочья) переменная `ServerChaosLevel`, растёт от событий `OnEssenceProduced` с `emotionType == "Fearful"`, немного падает от `"Joyful"`.
- При достижении порога — спавн боссовой модели, включение боевого режима: RemoteEvent на атаку `RequestAttackBoss()` с серверной валидацией дистанции/кулдауна урона.
- По завершении (победа/тайм-аут) — распределение наград всем участникам пропорционально вкладу (хранится временный `Map<Player, damageDealt>`, очищается по завершении ивента).
- Ивент должен корректно обрабатывать выход игроков из игры посреди боя (не терять их вклад для награды, если они успели выйти после урона, — награда выдаётся синхронно в момент завершения ивента только тем, кто ещё в сервере; при выходе до завершения — начисление на сохранённый профиль при следующем входе, если решено это поддерживать).

### 5.6 PvPRaidSystem (сервер)
- `RequestRaidStart(attacker, targetPlayer)` — проверка, что цель не под щитом, не на кулдауне, что атакующий физически зашёл в инстанс фабрики цели (загружается отдельный клон workspace-модели фабрики жертвы, а не сама «живая» фабрика владельца — чтобы не блокировать данные владельца, если он офлайн).
- Ограничение потерь: сервер считает максимум `min(target.Essence * 0.15, HardCap)` как верхнюю границу похищаемой суммы.
- Guards (стражи) — простые NPC/турели, влияющие на шанс успеха или на % украденного через формулу защиты из `MonetizationConfig`/`Config` (не в PvP-конфиге напрямую, чтобы не путать с ценами).

### 5.7 MonetizationSystem (сервер)
- Геймпассы: проверка владения через `MarketplaceService:UserOwnsGamePassAsync`, кэшируется в профиль при входе, чтобы не дёргать API на каждую проверку в геймплейном коде.
- Дев-продукты: `ProcessReceipt` **обязан** быть идемпотентным (Roblox может повторно вызвать callback) — использовать уникальный `PurchaseId` и лог обработанных покупок в DataStore, чтобы не выдать товар дважды или не потерять выдачу при сбое.
- Публикация odds для коконов: хранить таблицу шансов в `PetRarityConfig` как единственный источник правды, и генерировать из неё текст для UI автоматически (чтобы цифры в интерфейсе никогда не разъехались с реальной логикой ролла).

### 5.8 UI / HUD (клиент)
- HUD: счётчик Essence, индикатор Хаоса сервера, мини-инвентарь петов, кнопка Rebirth (активна только при достижении порога — с прогресс-баром до него).
- ShopUI: вкладки «Геймпассы» / «Разовые покупки» / «Сезонный пропуск», с явным отображением цены в Robux и (для рандомизированных предметов) — таблицы шансов.
- ChaosEventUI: полноэкранный оверлей полосы здоровья босса + личный вклад игрока, чтобы мотивировать участие.

## 6. Персистентность данных
- Профиль загружается при `PlayerAdded` через сессионно-блокирующую обёртку (ProfileStore/ProfileService-класс), исключающую одновременную загрузку одного профиля на двух серверах (защита от дюпа при телепортах/сбоях).
- Автосохранение с интервалом (например, каждые 3–5 минут) + принудительное сохранение при `PlayerRemoving` и `game:BindToClose`.
- Резервная стратегия: хранить последние N снапшотов через `DataStore:ListVersionsAsync` — возможность отката при массовом баге в проде.

## 7. Безопасность и анти-чит
- Все RemoteEvent-обработчики на сервере проверяют: тип аргументов, разумные диапазоны значений, частоту вызовов (rate limiting per player — простая реализация через таблицу временных меток).
- Никаких вычислений цены/награды на клиенте, которые потом «докладываются» серверу как факт — сервер всегда пересчитывает сам.
- Логирование подозрительной активности (например, попытка вызвать `PurchaseUpgrade` с несуществующим id) в отдельный DataStore/внешний лог для последующего ревью.

## 8. Производительность
- Стриминг контента (`Workspace.StreamingEnabled = true`) для больших локаций биомов.
- Object pooling для визуальных эффектов сбора фрагментов и частиц (не создавать/уничтожать Instance на каждый чих — переиспользовать пул).
- Ограничение количества одновременно видимых петов других игроков в кадре (LOD/упрощённая отрисовка на расстоянии) — критично при высоком онлайне на сервере во время Хаос-ивента.

## 9. Аналитика и телеметрия
- Кастомные события через Roblox Analytics API (или собственный лёгкий лог в DataStore/внешний сервис через HttpService, если нужен более гибкий дашборд): начало/конец rebirth, покупка каждого товара, участие в Хаос-ивенте, PvP-атаки.
- Обязательно фиксировать funnel первых 10 минут новой сессии (первый сбор → первая переработка → первый апгрейд → первый пет) — это стандартная точка отвала в симуляторах, и без данных её не починить.

## 10. Локализация
- Основной язык — русский (целевой рынок РФ/СНГ по GDD), английский — вторичный для доступа к глобальной аудитории Roblox.
- Все строки UI вынесены в отдельную таблицу локализации (не хардкод в UI-модулях), чтобы добавление языка не требовало правки логики.

## 11. Фазы разработки (ориентир)

| Фаза | Содержание | Условный срок |
|---|---|---|
| MVP | CollectionSystem, FactorySystem (без конвейерной задержки-фичи), базовые апгрейды, DataStore-сохранение, 1 биом, 3 пета без мутаций | 3–5 недель соло-разработки |
| Alpha | PetSystem с редкостями/мутациями, RebirthSystem, 2-й биом, базовый ShopUI и геймпассы | +2–3 недели |
| Beta | ChaosBossSystem, MonetizationSystem полностью (дев-продукты, odds), 3–4 биома | +3–4 недели |
| Live-ops запуск | PvPRaidSystem, сезонный пропуск, аналитика, полировка UI/арт | +2–3 недели |

*Сроки крайне ориентировочные и сильно зависят от доступного арт-контента; технический код при соло-разработке с Claude Code обычно не является узким местом — им становится арт/анимации.*
